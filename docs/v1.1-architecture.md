# Code Agent v1.1 architecture

This document describes the implementation contracts that should remain true
when v1.1 is extended. The Anthropic live path is intentionally outside this
milestone until credentials are available.

## 1. Main-loop policy

The engine remains a fact-driven state machine. Transient deltas and progress
events are UI-only; decisions that must survive a crash are facts reduced into
`AgentState` and copied into state snapshots.

After each tool batch the engine performs, in order:

1. reduce tool results and update bounded call/outcome fingerprints;
2. detect repeated calls, repeated failures, or a no-progress cycle;
3. record a structured reflection when stagnation is detected or the periodic
   interval is reached;
4. detect a replan trigger and choose local repair or full re-approval;
5. check approved-plan constraints;
6. begin the next model turn with the latest reflection and current execution
   strategy in the system instructions.

Reflection is deliberately not appended repeatedly to conversation history.
It is a bounded durable record and is projected into the next system prompt.
This lets it influence the model without making context compaction call the
summarizer more often.

Execution strategy only tightens during a run:

| Strategy | Trigger | Runtime effect |
|---|---|---|
| `normal` | healthy budget and progress | normal output budget |
| `conservative` | <=40% minimum budget, repeated failed batches or stagnation | max 2,048 output tokens; batch reads, no speculative scope |
| `critical` | <=15% minimum call/turn budget | max 1,024 output tokens; completion-critical work only |

The transition is journaled as `strategy.adapted`; replay never recomputes an
old decision from wall-clock time.

## 2. Unified tool contract

`defineTool` exposes one lifecycle:

```text
schema -> semantic validation -> permission -> live preconditions
       -> execute -> postconditions -> observation -> serialize/bound
```

- Preconditions describe live state that must hold at the execution boundary.
- Postconditions verify the actual outcome before a side effect is committed
  in the idempotency ledger.
- Observation is a small, redacted object with a summary and stable fields.
  It is stored in `ToolCallResult` and sent to the model in a JSON envelope.
- A failed precondition means the tool did not run.
- A failed postcondition means execution may already have changed external
  state. Workspace facts are persisted, the idempotency record stays unknown,
  and blind retry is forbidden.

Core file tools verify content versions after Read/Edit/Write/ApplyPatch.
New tools should provide domain postconditions and useful observation fields;
consumers must not parse the human serializer to make policy decisions.

## 3. Code intelligence

`CodeIntelligenceService` owns one lazy repository snapshot shared by all code
tools. The snapshot:

- scans supported TS/JS extensions in deterministic path order;
- skips symlinks, vendor/generated/session directories and oversized files;
- extracts definitions and references with bounded lexical analysis;
- derives a conservative direct-call graph from function/method blocks;
- is invalidated whenever ToolRuntime observes `workspace.changed`.

Tools:

- `CodeSymbols`: ranked definition search;
- `FindReferences`: occurrences with definition markers;
- `CallGraph`: explicit nodes and directed edges, optionally caller-focused;
- `CodeDiagnostics`: workspace TypeScript `tsc --noEmit` when available, else
  `node --check` for a requested JavaScript file.

This is honest lexical intelligence, not an LSP substitute. A future LSP
adapter can implement the same tool outputs without changing engine policy.

## 4. Local plan repair

Low-impact replans no longer merely record a message. When an approved plan
has steps, the engine enables `PlanRepair` for the open low-impact replan.

`PlanRepair` must:

- target the current approved plan version and exactly one existing step;
- keep the step id and dependencies unchanged;
- reject files outside the union of the approved plan's file scope;
- preserve every unaffected step and all acceptance criteria;
- create a new plan version with `bounded_local_repair` authorization;
- supersede the old version and keep the derived version approved;
- migrate tasks to the new version, reopening and clearing evidence only for
  tasks bound to the repaired step;
- emit `replan.adjustment.applied` to close the durable replan state.

Scope expansion, repeated implementation failure, or any high-impact change
still follows `PlanPropose -> ExitPlanMode -> human approval`, with write tools
locked until approval.

## 5. Recovery invariants

Snapshots include recent fingerprints, outcome signatures, stagnation count,
reflection counters, progress point, strategy and bounded reflection records.
Older snapshots omit these fields and restore safe defaults. New facts are in
the fact-type allowlist and flow only through the reducer.

The following invariants must stay tested:

- one accepted tool call has exactly one terminal result;
- structured observations are redacted and bounded;
- postcondition failure never marks a side effect committed;
- identical recovered state yields the same stagnation decision;
- a local repair cannot expand file scope or mutate unaffected steps;
- snapshot-plus-tail recovery equals full fact replay.

## 6. Configuration

Example `agent.config.json`:

```json
{
  "intelligence": {
    "enabled": true,
    "reflectionInterval": 8,
    "completionReflection": false
  },
  "replan": {
    "failureThreshold": 3,
    "conflictThreshold": 3,
    "scopeRatio": 2,
    "budgetPressureRatio": 0.15
  }
}
```

`completionReflection` is opt-in because it deliberately consumes one extra
model turn before accepting a no-tool completion. Periodic, stagnation,
replan and verification reflection remain active when intelligence is enabled.
