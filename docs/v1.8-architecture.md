# Code Agent v1.8 architecture

v1.8 makes the workspace-local reflection policy replay-stable. v1.6 could
derive a deterministic profile from historical `reflection.recorded` /
`reflection.evaluated` pairs, but every process start scanned mutable history
again. Deleting, replacing or later completing an old session could therefore
change the observation window used by future reflections in the same session.

v1.8.0 persists the selected profile and its bounded provenance before the
first model request, originally restoring it through a V4 snapshot, and
tightens the sample state machine so adaptive history is built only from
possible, single-flight outcomes. v1.8.2 advances snapshot-tail compatibility
to V5 so durable workspace-mutation verification cannot disappear behind an
older checkpoint. It also closes model-configuration and automated-release
boundaries described below.

## 1. Durable selection pipeline

```text
same-workspace historical journals
  -> loader sequence/checksum/type validation
  -> full production-reducer replay
  -> unique recorded/evaluated reflection pairs
  -> stable trigger/action aggregation
  -> canonical profile + source manifest
  -> flush outcome.calibration.selected
  -> reduced AgentState is the runtime authority
  -> bounded reflection window adjustment
```

`outcome.calibration.selected` contains:

- algorithm `reflection-window-v1` and schema version;
- origin (`history_scan`, `legacy_backfill` or test-only `test_injected`);
- scan status (`complete`, `no_history` or `history_unavailable`);
- the fixed ISO cutoff and normalized `minSamples` / `maxSessions` policy;
- the complete canonical profile, including its aggregate hash;
- a stable source manifest with session ID, last considered sequence, sample
  count and SHA-256 sample hash;
- a full SHA-256 selection hash over every field above.

The fact contains counts and hashes, not prompts, repository content, tool
output or credentials. Even an empty successful scan is selected explicitly;
an empty pin is different from calibration being disabled.

## 2. Boot and configuration precedence

The effective order is:

```text
explicit runtime disable
  > durable selection already present in this session
  > test/evaluator injection
  > a new workspace history scan
```

- A new enabled persistent session scans once, writes `run.started`, flushes
  one selection fact, and only then can assemble a model request.
- A resumed v1.8 session reuses the durable selection. It does not scan again,
  and a test injection or changed history cannot replace the pin.
- A pre-v1.8 session receives one `legacy_backfill` selection on its first
  enabled persistent resume. The pin explains only reflections created after
  that upgrade boundary; it does not retroactively claim provenance for older
  decisions.
- `outcomeCalibrationEnabled: false` suppresses use of an existing selection
  but does not delete it. Re-enabling the same session restores the original
  pin. A fresh disabled session does not fabricate an empty selection; its
  first later enabled start may create one.
- `persist: false` can still use a test-injected profile in memory, but it has
  no durable provenance and is not presented as replay-stable.

Once a persistent selection exists, the `AgentEngine` reads its profile from
reduced `AgentState`; the composition-root scan result is no longer the final
authority.

## 3. History and sample trust boundary

The scanner accepts sample-bearing sessions only after all of these checks:

- the journal is a regular file under this workspace's `.agent/sessions`
  tree, not a symlink/junction escape, and is at most 16 MiB;
- the first trusted fact is `run.started`;
- envelopes have known fact types, canonical ISO timestamps, continuous
  sequence numbers and valid per-event checksums;
- recovery diagnostics use the real workspace root, so workspace-relative and
  validated in-workspace absolute paths replay under the same boundary;
- the complete journal, not only a snapshot tail, replays through the current
  production reducer without an invariant failure;
- the session is not the current session or a degraded recovery branch;
- each evaluation references a prior decision-bearing reflection and neither
  reflection nor evaluation is duplicated;
- decision-bearing records bind every task, workspace, tool and Evidence
  baseline counter to the reduced state, and overlapping pending reflections
  make the entire history source ineligible;
- the durable tool-call delta equals `toolCallsObserved`;
- an ineffective result has reached its recorded window and has no fact-level
  progress; an effective result has both a signal and recomputable task,
  evidence or successful-tool progress.

Invalid, corrupt and sample-free candidates do not consume the usable
`maxSessions` quota. Directory discovery is still O(number of session
directories); `maxSessions` bounds accepted, fully loaded sample sources, not
the initial directory listing.

A `run.terminated` fact is not required. A journal interrupted after a fully
durable, semantically valid reflection/evaluation pair may contribute that
pair.

## 4. Single-flight reflection feedback

Before v1.8, the supervisor evaluated only the newest reflection. With a short
reflection interval and a longer evaluation window, a newer checkpoint could
replace an unevaluated no-progress baseline. Effective outcomes could complete
early while ineffective outcomes disappeared, biasing the profile upward.

v1.8 admits at most one eligible, unevaluated decision-bearing reflection at a
time. The supervisor evaluates the oldest pending record. Until it becomes
effective or reaches its no-progress window, another decision-bearing
reflection is not recorded. Each accepted evaluation is unique and paired by
the reducer.

This is a data-quality and loop-control invariant, not a model call. Reflection
records are still generated deterministically from reduced runtime facts.

## 5. Bounded adaptive-policy semantics

Profiles group samples by `(reflection trigger, SupervisorAction)`. The
minimum-sample gate and Laplace-smoothed descriptive rate retain the v1.6
rules:

- rate `>= 0.75`: observation window `+1`;
- rate `<= 0.40`: observation window `-1`;
- otherwise: no change;
- final window remains within `1..20`.

A reflection calibrated from a durable selection records its selection hash,
profile hash, base window, delta and final window. This makes the individual
decision attributable during full replay and evaluation. A `persist: false`
test injection may tune an in-memory window but deliberately does not claim
durable attribution.

The window is a **bounded policy input**, not a harmless display hint. Moving
the evaluation point by one call may indirectly make a later deterministic
repair/replan response happen one call earlier or later. It never directly
rewrites the current typed Supervisor action, target or success signals, and it
cannot expand authority or bypass:

- mode, permission, path/shell policy or ToolRuntime contracts;
- plan approval, write locks or reapproval;
- scope and active-plan constraints;
- Evidence freshness, Completion Gate or verifier verdicts;
- turn/model/tool/time budgets.

The profile is a local heuristic summary. Laplace smoothing is not a calibrated
probability, the observations are not causal, and this is not a learned reward
model or policy optimizer.

## 6. V5 snapshot and strict recovery

Snapshot schema V4 introduced persistence of the full calibration selection
alongside the V3 policy state. V5 retains that provenance and additionally
persists the workspace revision plus any pending mutation-verification
obligation. Only V5 uses snapshot-plus-tail fast recovery. V1-V4 checkpoints
fall back to full fact replay, preventing an older snapshot from hiding either
the earlier selection fact or a later completion obligation.

Recovery requires:

- at most one selection fact in the full trusted journal prefix;
- a valid algorithm, source manifest, policy/profile counts and hashes;
- exact equality when the journal selection belongs to the V5 snapshot prefix;
  a selection appended after that snapshot is recovered and validated from the
  tail instead;
- exact equality between the selection recovered into state and the runtime's
  boot selection;
- a non-negative integer workspace revision and a structurally valid pending
  obligation whose revision, scope, paths and source records agree with the
  restored state.

Duplicate, malformed, tampered or snapshot-mismatched selections, revisions or
obligations become typed recovery failures. They never silently trigger a
fresh scan, empty-profile fallback or verification reset. A bootstrap journal
containing only `run.started` plus a selection is still considered unused and
can be cleaned up safely.

## 7. Offline verification contract

The v1.8 release gate covers:

- positive history pin: `3/3 effective`, window `3 -> 4`, then history is
  replaced by an opposite profile and resume still uses the original hash;
- empty history pin: later history cannot turn the pinned empty profile into a
  non-empty one;
- explicit-disable precedence: the pin remains auditable but is not projected
  or applied until re-enabled;
- V5 snapshot-plus-tail and full replay convergence, with V1-V4 checkpoints
  taking the legacy full-replay path;
- single-flight no-progress evaluation at the full window;
- invalid baseline/outcome/pair, overlapping reflection, duplicate selection,
  unknown or unhashed extra field, bad hash, forged attribution, unknown fact
  and snapshot mismatch rejection;
- canonical traces include selection origin/hash and calibrated reflection
  windows, so repeated runs cannot hide policy drift.

All scenarios are scripted and offline. They exercise the real composition
root, engine, reducer, journal, policy and recovery code without an API key.

The historical v1.8.0 verification snapshot recorded on 2026-08-16 is:

- typecheck passed;
- 43/43 test files and 393/393 tests passed;
- statements/lines coverage 81.67%, branches 80.08%, functions 89.07%;
- Agent Eval 14 scenarios x 2 runs: 28/28 passed, all six scorecard dimensions
  and the overall score at 100, with identical per-scenario fact traces;
- retrieval regression: 6 file-level cases at Recall@10 1.0 and MRR 0.9167,
  4/4 graph cases, citation-format integrity 1.0, stale-hit rate 0 and an
  estimated 4,047 context tokens;
- secret scan, build and package allowlist checks passed.

These are small, checked-in regression suites. They prove the stated offline
contracts, not general model intelligence, provider availability, semantic
faithfulness or production reliability.

## 8. Durable mutation completion contract

An explicit approved plan remains the source of its acceptance criteria. V5
adds a minimum verification contract for every workspace mutation, whether or
not a plan exists. The contract is durable state rather than an inference from
compressible model messages or successful tool results.

After validation, permission, preconditions and idempotency adjudication, but
before execution, `ToolRuntime` derives the effective mutation scope and
synchronously flushes `workspace.mutation.started` to the journal. The reducer
increments the workspace revision at attempt time, records the source as
`unknown`, and opens or extends `workspace.pendingVerification`. Only after
that awaited persistence may the external side effect begin. A later
`workspace.changed` fact marks the matching source `changed` and adds its
canonical workspace-relative path.

Built-in `Write`, `Edit` and `ApplyPatch` calls declare exact path scope.
Mutating Shell calls declare whole-workspace scope because their exact write
set cannot be trusted in advance. A custom non-read-only tool that exposes a
workspace, file or workspace-process write resource but omits a declaration
receives the same fail-closed whole-workspace obligation. Idempotently
deduplicated operations that never execute do not open a new attempt.

Because the obligation is opened before execution, it remains accurate when:

- a write occurs but a postcondition fails;
- a tool writes partially and then throws;
- a Shell or custom tool has an unknown effect;
- context is compacted, the process stops after the flush, or recovery resumes
  through full replay or a V5 snapshot plus its tail;
- the run ends abnormally because of abort, budget, model or recovery failure.

Every later mutation advances the revision again, so pre-mutation evidence
cannot satisfy the current obligation. Clean `completed` status requires one
or more usable receipts that collectively establish all of the following:

- a signed, passed runtime observation from the same session and run;
- the same canonical workspace root and exact current workspace revision;
- an observed `FileAssert`, `DiffAssert`, or recognized test/build/lint/
  typecheck command, rather than a model-declared `evidenceKind`;
- bindings that collectively cover every known changed path. A whole-workspace
  obligation requires at least one workspace-wide validator. Narrow `rg` or
  `grep` assertions must mention the exact path they bind.

Version/help output, dry-run/no-test skip flags, compound Shell syntax, command
substitution and arbitrary successful no-ops are not verification. Multiple
path-bound receipts may be aggregated, but stale, cross-run, cross-session,
cross-root or cross-revision evidence is rejected. Risk-based independent
verification is an additional L2 gate after this relevant L1 evidence; the
presence or success of a verifier cannot bypass the mutation obligation.

If the bounded repair opportunity still produces no relevant proof, the
honest terminal is `completed_with_unverified_items`. Both that terminal and a
normal `completed` terminal close the request boundary and clear the pending
obligation for the next unrelated human task. Abnormal terminals retain it for
recovery continuation.

Completion reflection also respects the existing single-flight invariant. If
an older reflection is still pending and recording a completion reflection is
a no-op, the engine proceeds to the completion gate instead of emitting a
fake `reflection_requested` transition and consuming turns without progress.

## 9. Security and automated release gates

### Credential and retrieval trust

A model connection is one atomic `(API key, provider, model, base URL)` trust
bundle owned by the first eligible source. Environment, explicit/`AGENT_CONFIG`,
user, workspace and installation sources are considered in their documented
model order; fields are never merged across them. Any source that claims a
bundle but omits required key/model fields fails closed. A model-only verifier
override may reuse the exact main route, while a provider or endpoint change
requires an isolated verifier key. See
[`model-configuration.md`](model-configuration.md) for the complete rules.

`code-agent setup` hides API-key input, removes it from readline history,
restores the caller's prior history afterward and atomically replaces the
user-level model section. The retriever service and `RefreshCodeIndex` also
perform symlink/junction-aware realpath containment so a workspace-controlled
refresh cannot read outside the workspace.

### Secret, evaluation and package gates

Staged scanning reads the exact Git index blob for every selected add, copy,
modify, rename or type-change path. All scan modes load candidates as Buffers
without an extension allowlist and skip only NUL-containing binary content;
the whole-file exemption set is empty. Git selection/blob failures,
filesystem-read errors, realpath escapes and an unexpected empty text set fail
closed. Only a positively identified non-Git directory may fall back to a full
tree walk, and only the pre-commit wrapper explicitly permits an intentionally
empty staged set.

`secret-scan:package` scans tracked candidates plus freshly built `dist/`.
`eval:ci` parses only its documented flags, runs the deterministic Agent and
retrieval gates with `--no-write`, and rejects unknown arguments. Tag builds
must pass `check:release-tag`, which compares `vX.Y.Z` with `package.json`.
Finally, one Ubuntu Node 22 CI job runs standard `npm pack` without
`--ignore-scripts`: this proves the real `prepack` lifecycle executes the
offline evaluations, build, package secret scan and tarball allowlist. The
six-platform install matrix uses `--ignore-scripts` only after those lifecycle
gates have been exercised once.

## 10. Deliberate boundary

The journal checksum validates the current `seq + event` integrity model;
it is not an adversarial tamper-proof hash chain and does not prove fsync or
arbitrary power-loss durability. Source manifests explain the facts selected
by this implementation, not the causal quality of those observations.

v1.8 does not add OS sandboxing, external telemetry, a policy model, an
embedding service, a real-provider benchmark or process-level exactly-once
proof. The Anthropic adapter and protocol tests remain available, but
credentialed Anthropic live smoke is explicitly deferred because no API key is
available.
