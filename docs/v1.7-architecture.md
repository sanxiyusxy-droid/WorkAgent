# Code Agent v1.7 architecture

v1.7 turns the PlanSupervisor's typed next action into an execution contract.
Before this version, the action was durable and visible in the prompt, but the
provider still saw the ordinary mode-level tool list and `ToolRuntime` did not
know which action produced that request. A stale or adversarial tool call could
therefore ignore the supervisor hint and reach the permission pipeline.

## 1. Turn-frozen pipeline

```text
reduced facts -> durable plan.health.assessed / SupervisorAction
registry + mode + write lock + durable replan state
  -> deterministic ToolExecutionLane (stable order + SHA-256 hash)
  -> flushed tool.lane.selected audit fact
  -> model-facing tool schemas
  -> model tool-call batch
  -> ToolRuntime validates the SAME frozen lane before schema/policy/effect
```

The engine creates one immutable projection for a model request and passes the
same object to the following tool batch. It does not recalculate the lane after
the model responds, so prompt projection and runtime enforcement cannot diverge
because of an intervening state change. The next loop iteration derives a new
lane from the newest reduced facts.

`tool.lane.selected` is flushed before request assembly. It proves which lane
the engine selected for the request boundary; it does not prove that a provider
received or completed that request.

## 2. Lane policy

| Supervisor action | Lane | Capability policy |
|---|---|---|
| `continue_step` | open | Preserve the mode/write-lock candidate set for implementation. |
| `resolve_blocker` | open | Preserve diagnostic escape paths; normal policy remains authoritative. |
| `gather_evidence` | evidence | Inspection, retrieval, evidence assertions, criterion-bound `Shell` and `TaskUpdate`; direct file-edit tools are withheld. |
| `run_verification` | verification | Inspection, evidence assertions and criterion-bound `Shell`; task mutation and direct file edits are withheld. Plain text hands control to Completion Gate and the independent verifier. |
| `repair_plan` | plan repair | Before durable replan activation, inspection plus plan/task repair tools are available. While `replanning=true`, task mutation is frozen and only inspection plus plan persistence/approval tools remain. |
| `request_reapproval` | approval | Inspection plus `PlanPropose`/`ExitPlanMode`; task mutation and workspace writes remain locked. |
| `finish` | finish | Inspection and evidence assertions only; no new workspace changes. |

The action layer is intentionally asymmetric. It is strict at lifecycle
boundaries where a write is clearly out of stage, but keeps implementation and
diagnostic exits open for `continue_step` and `resolve_blocker`. An action may
only remove capabilities; it never grants one.

`Shell` is input-constrained in the evidence and verification lanes: it must
carry at least one non-empty `criterionIds` value before semantic validation or
permission runs. `ShellReadOnly` remains available for unbound observations.
The binding expresses intent only: it does not prove that an ID belongs to the
active plan, that a command is a valid oracle for that criterion, or that the
command is filesystem-isolated. Normal Shell analysis and permission policy
remain authoritative.

An independent verifier `FAIL` with repair budget remaining is recorded
atomically as a pending verification repair. The next assessment opens a
bounded `continue_step` implementation lane and includes the persisted failure
titles. Reapproval remains higher priority, so the repair state cannot bypass a
write lock. A new plan approval invalidates an old verdict and repair state.

## 3. Authority intersection and runtime enforcement

```text
reachable = registered tools
          intersect mode projection
          intersect write-lock projection
          intersect supervisor-action projection
```

`ToolRuntime` checks mode availability, the frozen write-lock projection and
the lane allow-list before permission or execution. It treats `allowedTools` as
the authority; `blockedTools` is audit data only. A second live write-lock check
remains in place to catch changes after prompt assembly.

After routing, every existing layer still runs in its original order: schema
validation, lane input constraint, semantic validation, permission, live
preconditions, abort, write lock/idempotency, execute, postconditions,
observation and bounded serialization. The lane cannot auto-approve a tool,
weaken path or shell policy, refresh stale Evidence, approve a plan or pass
Completion Gate.

`TOOL_NOT_AVAILABLE_FOR_ACTION` is a normal paired tool result. It is emitted
before permission, so a forged hidden call cannot cause an approval prompt or
side effect. Its content includes the frozen action and projection hash.
Unknown or malformed supervisor actions fail closed during reduction, snapshot
restore and lane construction rather than falling back to the open lane.

## 4. Durable audit and replay

`tool.lane.selected` stores only:

- schema version, turn ID and plan-health signature;
- typed action and lane name;
- mode, write-lock and replanning flags;
- stable allowed/blocked tool-name arrays;
- a canonical 16-hex SHA-256 prefix.

It carries no prompt text, tool input, repository content or secret. The
reducer treats it as audit-only because the next route is derived from reduced
state. It records selection provenance, not provider delivery.

v1.7 introduces snapshot schema V3. It persists current-plan scoped touched
files, the last loop transition and pending verification repair state in
addition to the existing state. V3 snapshot-plus-tail and full replay converge.
Older V2 snapshots are accepted but deliberately use full replay so a missing
V3 field cannot silently weaken scope or recovery policy.

Recovery also reconstructs accepted-call lifecycle state from durable
assistant `tool_call` blocks. If a crash leaves only a prefix of a multi-call
batch accepted, resume synthesizes the missing accepted and terminal results;
it does not execute those previously unaccepted calls. Invalid snapshots and
unknown actions become a typed recovery diagnosis rather than an uncaught
restore exception.

## 5. Plan, scope and completion consistency

- Low-impact `replan.requested` state always projects `repair_plan` until a
  durable adjustment closes it; normal implementation tools cannot reappear
  merely because the trigger counters were reset.
- Scope drift is calculated from canonical workspace-relative paths touched
  since the current plan approval, not from all historical session changes.
- Completion and supervision use the same active-plan task selection, so
  retired tasks from superseded plans cannot block a later approved plan.
- Failed current-plan tasks and any open durable replan remain explicit
  Completion Gate requirements; returning plain text from a repair lane cannot
  turn either state into success.
- A valid `PASS` is required for verified completion. Persisted `FAIL` or
  `PARTIAL` cannot become success after resume, and a human follow-up can reopen
  the bounded repair/reverification path without bypassing plan approval.

## 6. Verification contract

Release coverage proves:

- stable ordering, hashing and deep-freeze behavior;
- action projection cannot reintroduce a mode/write-locked tool;
- provider schemas and the following Runtime batch share one projection;
- a forged hidden call is refused before permission and execution;
- allow-list fail-closed enforcement even if `blockedTools` is incomplete;
- typed frozen and live write-lock refusals;
- criterion-less evidence/verification Shell calls never reach permission;
- verifier-failure repair survives snapshot and full replay;
- V2 fallback, V3 replay, malformed-action rejection and partial multi-call
  recovery preserve protocol pairing;
- current-plan scope/task filtering is stable across reapproval;
- canonical fact traces remain deterministic across repeated offline runs.

The offline suite contains eleven declarative scenarios, each repeated twice.
The v1.7 scenario deliberately submits a stale `Write` after plan health
changes to `repair_plan`. It binds the exact request's schema to the same lane
hash used by the Runtime refusal and requires unchanged workspace content.

Local validation snapshot (2026-08-16): TypeScript typecheck passed; 43 test
files / 382 tests passed; V8 coverage was 81.41% statements/lines, 79.58%
branches and 88.48% functions. Agent Eval passed 22/22 runs with every
scorecard dimension at 100 and deterministic traces. Retrieval Eval passed its
six query and four graph cases (Recall@10 1.0, MRR 0.8333, graph hit rate 1.0,
citation-field integrity 1.0 and stale hit rate 0). Secret scan, build and
package allow-list checks also passed.

## 7. Deliberate boundary

This is orchestration policy, not an operating-system sandbox. `Shell` still
runs through the host shell when reachable and approved. `criterionIds` are not
a persisted command-oracle specification, and arbitrary Shell mutations are
not comprehensively converted into `workspace.changed` facts.

v1.7 proves named application-level protocol and replay cases; it does not
prove arbitrary process/power-loss exactly-once, fsync every side-effect window,
or atomic reconciliation of every multi-fact high-impact replan transition. It
also does not add a learned policy model, run a real-provider benchmark or
complete Anthropic credentialed smoke. Those production-reliability and
external-validation tracks remain deferred.
