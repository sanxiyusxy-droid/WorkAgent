# Code Agent v1.5 architecture

v1.5 adds an offline, deterministic evaluation and fault-injection layer for
the Agent main loop. It answers a different question from ordinary unit tests:
given a declared task or failure, does the real `AgentEngine` produce the right
terminal state, facts, policy decision, recovery result and resource usage?

No network or API credential is required. The Anthropic live smoke remains
deferred until credentials are available.

## 1. Evaluation pipeline

```text
agent-scenarios.json
  -> scripted model + explicit fault schedule
  -> real createRuntime / AgentEngine / tools / journal / reducer
  -> canonical fact trace + external workspace assertions
  -> per-run checks
  -> repeated-run determinism check
  -> scorecard + baseline gate
  -> one JSON report -> Markdown projection
```

The harness does not implement a second miniature Agent. It executes the same
composition root, engine, tools, scheduler, policy, snapshots and recovery
code used by the CLI. Only the model response, clock, IDs and temporary
workspace are controlled.

## 2. Declarative scenarios

`eval/agent-scenarios.json` is the checked-in specification. A scenario names:

- its driver (`agent` or one of four recovery drivers);
- initial files, mode and deterministic model turns;
- an optional model-fault schedule;
- bounded runtime configuration;
- expected terminal reasons, facts, tool results, files, policy decisions and
  request-time tool visibility;
- maximum model requests and tool calls.

The runner rejects duplicate IDs, unknown filters and invalid repeat counts.
Every run uses a new temporary directory and removes it in `finally`.

## 3. Scenario matrix

| Scenario | Contract exercised |
|---|---|
| healthy read | assistant/tool lifecycle and normal completion |
| retryable model fault | deterministic RATE_LIMIT injection and recovery |
| unknown tool | bounded failure result for an unregistered tool |
| version conflict replan | three stale versions produce one low-impact replan |
| repeated-call reflection | repeated reads produce stagnation and reflection facts |
| high-impact scope lock | scope drift supersedes approval and removes write tools |
| result-gap recovery | an orphan is closed and a durable result message is repaired |
| checksum corruption | replay stops at the last trusted envelope |
| snapshot recovery | V2 snapshot plus tail equals full replay |
| degraded branch | corrupt source stays unchanged and the branch remains read-only |

The catalog defaults to two runs per scenario. A scenario passes only when all
checks pass and every repeated run has the same canonical fact-trace hash.

## 4. Deterministic fault injection

`FaultInjectingModel` is a `ModelGateway` decorator. Its schedule uses a
one-based physical request occurrence and a typed `ModelError`:

```ts
{
  point: 'model_request',
  occurrence: 1,
  error: { code: 'RATE_LIMIT', retryAfterMs: 0, retryable: true }
}
```

An injected failure does not advance `ScriptedModel`, so the retry consumes
the same next logical answer. Duplicate or non-positive occurrences are
rejected, and `assertScheduleConsumed()` prevents a typo from creating a test
that claims to inject a fault but never reaches it.

Fault injection is opt-in evaluation infrastructure. Production model
gateways are unchanged.

## 5. Durable physical model attempts

Successful model messages already counted one model call. v1.5 adds the
`model.attempt.failed` fact for every failed physical request. It records:

- one-based attempt number;
- stable error code;
- whether policy retries or surfaces the error;
- bounded delay selected by retry policy.

The fact is flushed before retry backoff. Replay therefore restores both
`budget.used.modelCalls` and `recovery.modelRetries`; a failed request can no
longer disappear from the budget merely because it produced no assistant
message. The engine also refuses a retry that would exceed the remaining
physical model-call budget.

Provider `Retry-After` is clamped to the configured delay cap and to zero at
the lower bound. Default retry sleep observes the run `AbortSignal`, so
cancellation does not wait for the full provider delay.

## 6. Recovery hardening

Two defects exposed by the recovery matrix are fixed:

1. A degraded fork owns a new journal and starts at sequence 1. It does not
   adopt the corrupt source journal's next sequence or parent event ID.
2. `session.recovery.branch` is a state transition, not audit-only prose. Its
   reducer sets `degradedRecovery=true` and `mode=plan`; snapshots and later
   replay retain the permanent write lock.

The engine enforces that lock twice: write tools are removed from the
model-facing schema, and the runtime write gate rejects a forced call. The
source journal is checked byte-for-byte after the branch run.

## 7. Assertions and invariants

Each run always checks:

- an allowed terminal reason;
- no accepted tool call without a terminal result;
- exactly one terminal result for each call;
- declared model and tool budgets.

Scenarios then add policy-specific assertions such as exact replan cause,
reflection trigger, required/forbidden facts, file contents and tool-schema
visibility. Recovery drivers add last-trusted-sequence, synthetic-result,
source-integrity and replay-equivalence checks.

The canonical trace excludes volatile timestamps, durations and generated
event IDs, while retaining behavior that matters: tool order/results, model
failure policy, workspace changes, replan decisions, reflection outcomes,
strategy transitions, terminal reason and recovery provenance.

## 8. Scorecard and baseline

The report uses six dimensions:

| Dimension | Weight |
|---|---:|
| correctness | 30% |
| safety invariants | 20% |
| fault recovery | 20% |
| planning/reflection policy | 15% |
| budget efficiency | 10% |
| deterministic replay | 5% |

`eval/agent-baseline.json` is fail-closed for the checked-in suite: all rates
and the total score must be 100, and average tool use must stay within its
declared ceiling. The full suite is the release gate; filtered runs are for
diagnosis.

JSON is the only score source. Markdown is rendered from the same
`AgentEvalReport` object, so human and machine reports cannot calculate
different results. Operational timestamps and measured durations may differ;
determinism is intentionally judged on canonical behavior traces.

## 9. Commands

```sh
npm run eval                    # complete deterministic Agent gate
npm run eval:agent              # explicit alias
npm run eval:faults             # scenarios with a declared fault
npm run eval:retrieval          # offline RAG benchmark
npm run eval:all                # Agent gate, then RAG benchmark
npm run eval:live               # real-provider fixture tasks; needs credentials

npx tsx eval/agent-eval.ts --scenario recovery-snapshot --runs 3 --no-write
```

Normal offline runs write timestamped and `latest` JSON/Markdown files under
ignored `eval/results/`. `--no-write` prints JSON without creating artifacts.

The legacy real-model harness is now explicitly `eval:live`. It only marks a
task successful when the CLI exits normally, the Agent terminal is
`completed`, and all external checks pass. A timeout, non-zero exit or missing
journal can no longer be hidden by an already-passing repository check.

## 10. Required regression gates

Before a version is considered releasable:

1. typecheck must include `eval/**/*.ts`;
2. all unit and recovery tests must pass;
3. `npm run eval` must pass every scenario with identical repeated traces;
4. `npm run eval:retrieval` must retain its checked-in RAG baseline;
5. coverage, secret scan, build and package-content checks must pass.

Real-provider evaluation remains informative and credential-dependent; it is
not part of `prepack`.

## 11. Remaining boundary

v1.5 deliberately covers deterministic request-boundary model faults and the
highest-value journal recovery paths. It does not yet claim process-level
exactly-once behavior for every byte-level crash window. Future work can add a
child-process crash worker and injection points around journal fsync, tool
side effects, idempotency commit and tool-result-message persistence. A
mid-stream provider failure also still needs attempt-aware terminal rendering
if partial deltas must be hidden during retries.

Those additions should extend the same scenario/check/report contracts rather
than introduce a second evaluation system.
