# Code Agent v1.3 architecture

v1.3 turns the v1.2 Code RAG baseline into an explainable agentic retrieval
pipeline. The model still decides when to search and expand, but query rewrite,
candidate ranking, diversity, graph traversal, budgets and integrity checks are
runtime mechanisms rather than prompt-only suggestions.

## 1. Why this version exists

The v1.2 offline benchmark already had full Recall@10, so adding more raw
candidates would mostly increase tokens. Its weaker metric was MRR: the correct
file was usually present but not always near the top. v1.3 therefore targets
precision and context selection:

```text
original query
  -> deterministic query plan
  -> multi-variant BM25 + vector recall
  -> weighted RRF
  -> local feature reranker
  -> MMR diversity / per-file cap
  -> versioned cited hits
  -> optional source-ID context graph expansion
```

No additional model call is required. The local hash embedding remains an
offline vector baseline, not a learned semantic embedding.

## 2. Query plan

`QueryPlanner` creates a bounded `RetrievalQueryPlan`:

```ts
interface RetrievalQueryPlan {
  original: string
  normalized: string
  intent: 'implementation' | 'documentation' | 'tests' |
    'configuration' | 'unknown'
  terms: string[]
  identifiers: string[]
  expansions: string[]
  phrases: string[]
  variants: string[]
}
```

The original query is never discarded. Rewrite is deterministic and capped at
four variants so it cannot create an unbounded query fan-out. Domain expansion
is deliberately small: for example execution/pipeline can add `runtime`,
permission can add `policy`, and recovery/replay can add `session`/`journal`.
This improves code vocabulary matching without asking another LLM to invent a
query that may drift away from the user's request.

## 3. Recall and weighted RRF

Each variant independently produces a BM25 list and a vector list. The original
query contributes full RRF weight; derived variants use a lower weight. Scores
from different retrievers are never added directly:

```text
weighted RRF(d) = sum(weight_i / (60 + rank_i(d)))
```

The trace records BM25, vector and fused candidate counts. A bounded candidate
pool protects CPU even when the repository contains tens of thousands of
chunks.

## 4. Explainable local reranker

The reranker uses only inspectable features:

- proportion of query/expanded terms present in the chunk;
- query terms present in path and symbol names;
- exact quoted/full phrase match;
- bounded term-density score;
- BM25, vector and RRF priors;
- intent prior (`src` for implementation, tests for test intent, documents for
  documentation intent, configuration files for configuration intent).

Every hit exposes `metadata.ranking` with matched terms, path/symbol terms,
coverage, phrase match and intent boost. This is intentionally not presented as
a cross-encoder. A learned reranker can replace it later only after the offline
cases demonstrate a remaining precision bottleneck.

## 5. MMR and context diversity

Returning ten neighboring chunks from one large file often wastes context.
v1.3 applies Maximum Marginal Relevance after reranking:

```text
MMR = lambda * normalized_relevance
      - (1 - lambda) * max_similarity_to_selected
```

Similarity uses the existing normalized chunk vectors, with a same-file
penalty. `maxPerFile` provides a hard bound. Defaults are `lambda = 0.75` and
three chunks per file; both are bounded, and diversity can be disabled for
diagnosis. The final hit records both rerank and diversity scores.

## 6. Context graph expansion

`ExpandCodeContext` accepts source IDs returned by `SearchCodeIndex`. It does
not accept arbitrary file content as authority. The graph supports:

| Relation | Meaning |
|---|---|
| `adjacent` | previous/next chunk in the same versioned file |
| `imports` | files reached by relative import/require/from syntax |
| `calls` | indexed symbol chunks named by lexical call expressions |
| `imported_by` | files whose resolved relative import points to the seed |

Traversal is breadth-first with depth 1 or 2, a maximum of 50 returned chunks
and an independent character budget. An optional `focus` query scores target
paths/symbols before traversal, preventing a high-fan-out composition root from
using the entire budget on alphabetically early but irrelevant imports.

Import resolution is repository-local and extension-aware. Package aliases,
dynamic imports and dynamic dispatch may remain unresolved; the result is
explicitly lexical rather than a full language server graph.

## 7. Graph and citation integrity

Expansion returns explicit edges:

```ts
interface ContextEdge {
  fromSourceId: string
  toSourceId: string
  relation: 'adjacent' | 'imports' | 'calls' | 'imported_by'
  distance: number
}
```

The tool postcondition requires every edge endpoint to be a seed or returned
hit and every distance to remain within the requested depth. Expanded hits use
the same file SHA, repository version, line range, secret sanitization, trust
label and citation format as search hits. Indexed content still cannot be used
as an Edit precondition; `Read` must obtain the live version.

## 8. Retrieval trace

`SearchCodeIndex` now returns:

- the complete query plan;
- corpus, sparse, vector, fused, reranked and returned candidate counts;
- embedding provider, RRF constant, reranker and diversity algorithm IDs;
- configured per-file cap and end-to-end local duration;
- per-hit BM25/vector/RRF/rerank/diversity scores and ranking signals.

The trace is part of the normal tool result and journal. It makes questions
such as “why was this file first?” and “did query expansion explode?” answerable
without scraping prose or enabling a second debug pipeline.

## 9. Configuration

```json
{
  "retrieval": {
    "enabled": true,
    "refreshOnSearch": true,
    "maxFiles": 20000,
    "maxFileBytes": 1000000,
    "maxChunks": 60000,
    "maxPerFile": 3,
    "diversityLambda": 0.75
  }
}
```

Individual search calls may set `intent`, `rerank`, `diversity` and
`maxPerFile`. Overrides are schema-bounded and visible in the trace. Managed,
CLI, project and user configuration retain the existing merge precedence.

## 10. Evaluation

`npm run eval:retrieval` now gates two related tasks:

1. ranked retrieval: Recall@10, MRR, citations, freshness, context and latency;
2. context graph: whether a seed source expands to the expected imported code.

`eval/retrieval-baseline.json` requires MRR >= 0.75 and graph hit rate 100%, in
addition to the v1.2 citation/freshness/Recall gates. Evaluation case documents
are excluded from the index to prevent label leakage. The suite remains a small
deterministic regression set, not a claim of production-wide semantic quality.

## 11. Remaining boundary

The next version should not add more retrieval stages by default. Plausible
extensions are a learned `EmbeddingProvider`, a learned reranker, Git history
retrieval or repository ACL filtering. Each should be justified by a measured
failure mode and must keep source versioning, prompt-injection labeling,
budgets, traceability and recall-time security filtering intact.
