# Code Agent v1.4 architecture

v1.4 closes the feedback loop between planning, execution and reflection. The
runtime no longer records a recommendation and merely hopes that later tool
calls follow it. It derives a typed next action from durable facts, declares
observable success signals, evaluates the result, and escalates only after a
bounded recommendation window fails to produce progress.

This version adds no external model call. Anthropic live verification remains
deferred until credentials are available.

## 1. Main-loop lifecycle

The engine remains a fact-driven state machine:

```text
reduced state
  -> evaluate the latest reflection (when its window is ready)
  -> assess plan health (deduplicated by stable signature)
  -> adapt execution strategy if required
  -> assemble supervisor + reflection policy into the prompt
  -> model turn -> tool contracts -> reduced results
  -> supervise again before stagnation/replan decisions
  -> completion and verification gates
```

The second supervision pass matters. Replan policy observes the current tool
batch's facts instead of waiting for another model turn. Live execution and
journal replay still use the same reducer; neither path reconstructs decisions
from prose or wall-clock guesses.

## 2. Plan health assessment

`PlanSupervisor.assessPlanHealth` is a pure policy over:

- task status and dependency readiness;
- required criteria covered by usable, kind-matched, integrity-checked evidence;
- touched files outside approved plan scope;
- consecutive failed batches and stagnation facts;
- consecutive ineffective reflection outcomes;
- minimum remaining model-call, tool-call and turn budget;
- replan and approval-lock state.

It returns:

```ts
interface PlanHealthAssessment {
  id: string
  createdAt: string
  status: 'not_applicable' | 'healthy' | 'attention' | 'at_risk' | 'blocked'
  score: number
  signature: string
  metrics: PlanHealthMetrics
  findings: string[]
  decision: SupervisorDecision
}
```

The score is diagnostic rather than probabilistic. It starts at 100 and uses
bounded penalties for failed/blocked tasks, dependency dead ends, missing
evidence, scope drift, repeated failures, stagnation, ineffective reflections
and budget pressure. Hard states such as a failed task or pending plan approval
produce `blocked` regardless of the remaining numeric score.

## 3. Stable assessment facts

Raw remaining-budget ratios change after every call. Journaling each small
change would create noise without changing policy. The assessment therefore
exposes the exact ratio but its signature uses only the three policy bands:

| Band | Minimum remaining budget |
|---|---:|
| normal | above 40% |
| conservative | 15% to 40% |
| critical | at or below 15% |

The signature also includes health status, score, meaningful metrics, scope
drift and the typed decision. `plan.health.assessed` is persisted only when
that signature changes. Recovery can therefore prove which policy state was
active without filling the journal with per-call duplicates.

## 4. Typed next actions

`SupervisorDecision` separates policy from explanatory prose:

```ts
interface SupervisorDecision {
  action:
    | 'continue_step'
    | 'gather_evidence'
    | 'run_verification'
    | 'resolve_blocker'
    | 'repair_plan'
    | 'request_reapproval'
    | 'finish'
  rationale: string
  targetTaskId?: string
  targetStepId?: string
  successSignals: string[]
}
```

Decision precedence is conservative:

1. an approval lock requires a revised approved plan;
2. failed work, scope drift or ineffective advice requires the smallest repair;
3. an explicit blocker must be resolved or honestly terminated;
4. a dependency-ready task becomes the execution focus;
5. completed tasks with uncovered criteria gather evidence;
6. changed code without a verdict runs verification;
7. fully supported work is handed to the completion gate.

`finish` does not terminate the run. It means only that the evidence-driven
completion gate may decide; model prose still cannot bypass that gate.

## 5. Reflection as a testable decision

v1.1 reflections contained useful summaries but their recommendation was an
unstructured string. v1.4 retains that readable field and adds:

- action and optional target task/step;
- observable success signals;
- a bounded `evaluateAfterToolCalls` window;
- baselines for completed tasks, evidence receipts, successful tool calls and
  total tool calls.

The normal default window is three tool calls. Pre-v1.4 reflections do not have
the complete baseline and are deliberately left unevaluated rather than being
guessed from partial state.

## 6. Reflection effectiveness

`evaluateReflectionEffect` recognizes progress only from durable state:

- one or more additional completed tasks;
- one or more new evidence receipts;
- a successful tool call accompanied by a workspace, task or evidence
  progress fact.

Assistant text, a changed recommendation, and repeated successful reads are
not progress signals. A recommendation is recorded as `effective` immediately
after a fact-level signal. If no signal appears by the configured window, the
runtime persists an `ineffective` evaluation with a repair-oriented follow-up.

Evaluations are bounded to the latest 20 records. An effective result resets
the consecutive ineffective counter; an ineffective result increments it.

## 7. Escalation and replanning

The default `ineffectiveReflectionThreshold` is two. When two consecutive
evaluated recommendations fail and an approved plan exists, the replan detector
emits the `reflection_ineffective` cause.

This is a low-impact trigger:

- if the approved plan has steps, `PlanRepair` must replace exactly one step;
- unaffected steps, dependencies, acceptance criteria and file-scope union are
  preserved;
- a scope expansion still requires `PlanPropose`, `ExitPlanMode` and human
  approval;
- the existing maximum of two replans per run remains in force.

Two ineffective evaluations also qualify the execution strategy for
`conservative`. Strategy remains monotonic (`normal -> conservative ->
critical`) and recovery never relaxes an earlier persisted decision.

## 8. Prompt projection

The prompt receives a bounded supervisor block containing health status,
score, at most four findings, the typed next action, success signals and the
latest applicable reflection outcome. It explicitly states that it is a policy
hint and that completion still depends on tasks and evidence.

Supervisor and reflection data are projected into system instructions, not
appended repeatedly to conversation history. Context compaction therefore does
not need to summarize another copy after every turn.

## 9. Recovery contract

New fact types:

- `plan.health.assessed`;
- `reflection.evaluated`.

`StateSnapshotV2` now includes:

- full plan tasks (not only task IDs);
- the latest health assessment;
- bounded reflection evaluations;
- ineffective-reflection counters and the last evaluated reflection ID.

Persisting full tasks closes a previous snapshot gap: an in-memory run with
tasks can now resume from snapshot plus journal tail without losing task
bodies. Older snapshots omit these fields and restore empty collections and
zero counters safely.

## 10. Configuration

```json
{
  "intelligence": {
    "enabled": true,
    "reflectionInterval": 8,
    "reflectionEvaluationWindow": 3,
    "completionReflection": false
  },
  "replan": {
    "failureThreshold": 3,
    "conflictThreshold": 3,
    "scopeRatio": 2,
    "budgetPressureRatio": 0.15,
    "ineffectiveReflectionThreshold": 2
  }
}
```

The engine clamps the evaluation window to 1-20 tool calls. Layer precedence
remains managed, CLI, project, user and defaults.

## 11. Required invariants

Future changes must preserve these tests and contracts:

- identical fact state yields the same health signature and decision;
- raw per-call budget changes inside one band do not create assessment spam;
- a reflection is evaluated at most once;
- pre-v1.4 reflections are not retroactively guessed;
- only durable task/evidence/workspace progress can prove effectiveness;
- an effective outcome resets the ineffective counter;
- an ineffective threshold cannot bypass plan-repair scope constraints;
- snapshot-plus-tail recovery retains full tasks and supervision state;
- `finish` never bypasses the completion or verification gates.

## 12. Remaining boundary

The supervisor is a deterministic local policy, not a learned process-reward
model. A later version may add historical outcome calibration, Git-aware risk
features or an optional learned policy, but only behind the same typed decision,
fact provenance, bounded evaluation and replay contracts. The current version
does not justify another retrieval stage or an additional reflection model call.
