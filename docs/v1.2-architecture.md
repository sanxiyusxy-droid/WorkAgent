# Code Agent v1.2 architecture

v1.2 adds Code RAG without moving retrieval policy into `AgentEngine`. The
engine still sees ordinary read-only tool calls and structured results; index
construction, ranking, freshness and citations live behind a `Retriever`
interface. This keeps the main loop deterministic and lets the embedding
implementation evolve independently.

## 1. Scope and honest boundary

Included:

- code/document/configuration discovery with explicit extension allowlists;
- symbol/heading-aware chunks plus bounded overlapping fallback windows;
- BM25 sparse ranking, local vector ranking and RRF fusion;
- stable source citations tied to file versions and line ranges;
- persistent cache, incremental refresh and deletion synchronization;
- secret sanitization, prompt-injection trust labels and output bounds;
- an offline retrieval benchmark requiring no model API.

Not included:

- a learned semantic embedding model or external vector database;
- cross-repository/tenant ACLs;
- Git blame/history retrieval, graph-neighbor expansion or reranking models;
- automatic use of stale indexed text as an edit precondition.

The default `local-hash-v1-192` embedding is a deterministic feature-hash
vector over identifier subwords and character trigrams. It improves fuzzy code
matching and makes the vector/RRF path executable offline, but must not be
described as a learned semantic model.

## 2. Dependency direction

```text
AgentEngine
  -> ToolRegistry / ToolRuntime / ToolScheduler
       -> SearchCodeIndex | RefreshCodeIndex | CodeIndexStatus
            -> Retriever interface
                 -> CodeRetriever
                      -> chunker
                      -> BM25
                      -> EmbeddingProvider (local hash by default)
                      -> RRF
                      -> .agent/index/code-rag-v1.json
```

`AgentEngine` has no retrieval import and no vector-store state. Search results
are ordinary `tool.call.completed` facts, so existing journaling, replay,
output externalization and context compaction continue to work unchanged.

## 3. Index document

The on-disk document is derived data with schema version 1. It is safe to
delete and rebuild. Each file record stores size and mtime for cheap change
detection, a SHA-256 file version, and its chunks. Each chunk stores:

```ts
interface RetrievalChunk {
  sourceId: string
  uri: string
  version: string              // SHA-256 of raw file bytes
  repositoryVersion?: string   // Git HEAD when available
  kind: 'code' | 'documentation' | 'configuration'
  language: string
  symbol?: string
  startLine: number
  endLine: number
  content: string              // sanitized before persistence
  redacted: boolean
  indexedAt: string
  termFrequencies: Record<string, number>
  termCount: number
  embedding: number[]
}
```

`sourceId` hashes URI, file version, line range, symbol and fragment ordinal.
Changing the file therefore creates new IDs; unchanged chunks keep stable IDs
across process restarts. `indexVersion` hashes the sorted file/chunk manifest,
embedding provider and repository version.

## 4. Chunking

TypeScript/JavaScript and other supported code use top-level declaration
boundaries (function, class, interface, type, enum, namespace and common
language equivalents). Markdown uses headings. Files without reliable
boundaries use line windows.

Every chunk is bounded to 120 lines and 12,000 characters. Long regions use an
eight-line overlap so a boundary-spanning query is still recallable. The
chunker is intentionally lexical: a future AST implementation can replace it
behind the same chunk contract without changing tools or citations.

## 5. Hybrid ranking

For query terms `q`, BM25 uses `k1 = 1.5` and `b = 0.75`, with small exact
path/symbol boosts. The vector branch embeds both query and chunk into a
normalized 192-dimensional vector and uses cosine/dot-product similarity. A
minimum similarity threshold suppresses unrelated hash collisions.

The two rank lists are fused with Reciprocal Rank Fusion:

```text
RRF(document) = sum(1 / (60 + rank_i))
```

RRF avoids pretending BM25 and vector scores have the same scale. Search
returns each component score for diagnosis and deterministic tie-breaking by
`sourceId`. `limit` and `maxChars` independently bound hit count and injected
context.

## 6. Freshness state machine

```text
uninitialized -> full build
clean --workspace.changed(path)--> dirty(path)
dirty(path) --search/refresh--> incrementally replaced -> clean
clean --external metadata change--> incrementally replaced -> clean
clean --force--> full re-hash -> clean
```

Agent write facts invalidate both v1.1 code intelligence and v1.2 retrieval at
the Tool Runtime boundary. An auto search scans the supported file manifest,
reuses unchanged file records, rebuilds changed files and removes deleted
records. `freshness: cached` avoids the external metadata scan, except that
known dirty paths are never ignored. `freshness: force` re-reads and re-hashes
the full corpus.

The cache is written through a temporary file and rename. A missing, corrupt or
provider-incompatible cache is ignored and rebuilt rather than trusted.

## 7. Citation and edit boundary

A hit citation has this shape:

```text
[src:<sourceId>] path/to/file.ts:10-42@<short-file-sha>
```

The `SearchCodeIndex` postcondition checks source ID, full SHA version, line
range, trust label and citation agreement. This is a citation-integrity gate
for runtime-produced evidence; the model cannot invent a valid hit by prose
alone.

Indexed text is discovery context, not a write precondition. Before Edit, the
agent must call `Read` and use the current `fileVersion`. This prevents a stale
index result from overwriting a newer file.

## 8. Security

- `.git`, `.agent`, dependencies, generated output, virtual environments and
  vendor directories are excluded.
- Symlinks/junction entries are not followed during discovery.
- Known lockfiles, `agent.config.json` and sensitive configuration filenames
  are excluded.
- Credential-like text in otherwise valid source files is sanitized before it
  reaches embeddings, results or the persistent cache.
- Every hit is labeled `untrusted_repository_content`; the system prompt tells
  the model that retrieved text is data, not instruction.
- File, chunk, result-character and candidate limits bound CPU, memory and
  prompt growth.

This protects the documented single-user trusted-workspace model. It is not an
ACL boundary or an OS sandbox for hostile repositories.

## 9. Tools

| Tool | Purpose | Resource claim | Plan mode |
|---|---|---|---|
| `SearchCodeIndex` | hybrid retrieval with citations | index read | allowed |
| `RefreshCodeIndex` | full/incremental derived-index refresh | index write | allowed |
| `CodeIndexStatus` | generation/count/dirty diagnostics | index read | allowed |

Although refresh writes `.agent/index`, it is source-read-only: it cannot
modify user project files and therefore does not enter business-operation
idempotency. The scheduler resource claim still prevents index races, and the
retriever serializes cache generations internally.

## 10. Configuration

```json
{
  "retrieval": {
    "enabled": true,
    "refreshOnSearch": true,
    "maxFiles": 20000,
    "maxFileBytes": 1000000,
    "maxChunks": 60000
  }
}
```

Configuration follows the existing managed > CLI > project > user > defaults
precedence. Disabling retrieval removes all three tools and the service from
the composition root; no partial fallback index is created.

## 11. Evaluation

Run:

```sh
npm run eval:retrieval
```

The evaluator builds an in-memory index and reports Recall@10, MRR, citation
integrity, stale-hit rate, mean latency, estimated context tokens and index
build statistics. It verifies returned file hashes against live bytes. These
small checked-in cases are guarded by `eval/retrieval-baseline.json`; Recall,
MRR, citation/freshness or context-budget regressions fail the command. This is
not SWE-bench or proof of production semantic quality; resume claims should
quote the actual output of a recorded run rather than hard-code aspirational
percentages.

## 12. Next extension points

The next retrieval improvements should be evidence-driven:

1. replace `EmbeddingProvider` with a learned local/hosted model and rebuild
   the index when provider ID/dimensions change;
2. add a reranker only if Precision@K is the observed bottleneck;
3. add import/call-graph neighbor expansion using the existing code-intel
   service;
4. add Git history/blame as a separate retriever with its own source IDs;
5. enforce repository/tenant ACL filtering at recall time before any hit can
   enter fusion or the model context.
